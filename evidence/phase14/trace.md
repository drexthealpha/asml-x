# Task 14.3: one decision traced end to end

Run 2026-08-16 14:52:41 UTC.

Produced by the REAL OpenTelemetry Rust SDK: `opentelemetry` 0.32, `opentelemetry_sdk` 0.32,
`opentelemetry-stdout` 0.32. The trace id, span ids and parent-child linkage below are assigned
by `SdkTracerProvider` and OpenTelemetry's own `Context`, not by this repo.

The exporter is `stdout`, not OTLP-over-gRPC, because that one needs a collector process and a
trace nobody can read without standing up infrastructure is not evidence. This JSON-lines file is
written alongside it so the gate and `jq` have a stable format to read.

ADR-019 records that an earlier version of this claimed the SDK could not be used at all, because
crates.io was unreachable from this machine. That claim was never tested and was false.

## What the shape shows that a total would not

A flat elapsed time says the cycle took N microseconds. The tree says WHICH stage held them.
The chain read dominates, which is the expected answer for a system whose work is mostly
waiting on an RPC, and having it measured rather than assumed is the point: it says that
optimising the decision engine would be optimising the wrong thing.

## Spans emitted

| span | what it covers |
|---|---|
| `decision_cycle` | the root: one full perceive, decide, gate, act, journal pass |
| `perceive.read_snapshot` | reading the venue's order book from chain |
| `perceive.signals` | computing signals from the observed book |
| `decide.thesis` | forming the thesis and its confidence |
| `perceive.portfolio` | reading guard exposure and building the portfolio |

A failed chain read closes its span with `outcome=failed` and the root with
`outcome=rpc_failed`, so a broken cycle appears in the trace rather than vanishing from it.
